*   **Hooks:** No hooks from `hooks.py` are required. The logic is handled at the API controller level via the whitelist decorator, not through DocType events.

**3. Recommended Implementation Approach:**

1.  **Create Decorator:** In `utils/idempotency.py`, define a decorator `@idempotent_request`.
2.  **Decorator Logic:**
    *   It will retrieve the idempotency key from `frappe.request.headers`.
    *   It checks `frappe.cache()` using the key. If a value is found, it sets `frappe.response.update(cached_value)` and returns immediately.
    *   If no cache entry exists, it calls the decorated API function.
    *   Upon successful execution of the function, it will cache the contents of `frappe.response` with a 24-hour expiry (`ex=86400`).
3.  **Update API Endpoint:** In `api.py`, apply the `@idempotent_request` decorator to the existing booking creation function (e.g., `create_booking`).

**4. Edge Cases & Gotchas:**

*   **Error Handling:** The decorator must use a `try...except` block. If the booking logic fails, it must *not* cache the error response.
*   **Race Conditions:** To prevent duplicate creations from near-simultaneous requests, use a temporary lock. Before executing the main logic, set a short-lived key like `frappe.cache().set(key + ':lock', True, ex=10)`.
*   **Cache Invalidation:** The requirement is a 24-hour TTL, which Frappe's cache handles automatically. No manual invalidation logic is needed.
*   **Client Responsibility:** The brief should remind the developer that the UUID idempotency key must be generated by the client and is expected in the request.
