### Patterns discovered

   - `guestContext.name` → `guest_name` (step skip condition)
   - `guestContext.unit` → `unit`
   - `guestContext.arrival_date` → `check_in_date`
   - `guestContext.departure_date` → `check_out_date`
   - `guestContext.nights` → `nights`

   - `skip_if_guest_field` property on workflow step definition
   - `shouldSkipStep()` utility function checking if all specified fields are populated
   - Loop in `executeWorkflowStep()` (lines 440-451) consuming multiple consecutive skips

3. **Population Check Definition:** Field is considered "populated" if:
   - Value exists in collectedData (not undefined/null)
   - Value is non-empty after trimming whitespace
   - This prevents false positives from empty strings or whitespace

4. **Workflow Completion:** If all remaining steps are skipped (line 454), workflow ends gracefully and is marked complete

   - This happens at line 309-333 when `guest_id` exists in collectedData
   - For returning guests, must first identify them by phone/ID before skip logic engages

2. **Skip Field Name Mapping:** Must match collectedData key names, not guest profile field names:
   - Use `["guest_name"]` in skip_if_guest_field, NOT `["name"]`
   - The mapping is done externally in guest context loading code

3. **Test Architecture:** All skip logic validation is in-memory without database:
   - Tests mock WorkflowStep, WorkflowState, and Workflow interfaces
   - This validates skip logic independently of database/context loading
   - Integration with full booking flow would need separate E2E test
