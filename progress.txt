*   **Frappe API:** The core mechanism will be `frappe.cache()`. The loader will populate the cache, and the watcher will trigger a cache invalidation (`frappe.cache().delete_value(...)`).
*   **DocTypes:** No DocTypes will be modified directly. The reloaded configuration will dynamically alter the behavior of relevant DocTypes (e.g., `LHDN Payroll Settings`, `Payroll Entry`) for all new operations.

*   **Atomic Writes:** File writes may not be atomic. The `reload_config` function should include error handling (e.g., `try...except json.JSONDecodeError`) to prevent crashes from reading partially written files.
*   **Threading:** The watcher must run in a non-blocking background (daemon) thread to avoid halting the main Frappe server process.

### Patterns discovered

1. **Chokidar configuration:** Used `awaitWriteFinish` with 100ms thresholds to detect when file writing completes before emitting change events. Critical for Windows file system timing.

2. **Debouncing strategy:** Tracked pending reloads in a Map keyed by filename to prevent rapid successive reloads. Clear timeout and restart on new change within debounce window.

3. **Event-driven architecture:** ConfigStore already extends EventEmitter, so watcher hooks into existing 'reload' event system. No modification to core ConfigStore needed.

4. **Preserve in-flight conversations:** By emitting events rather than directly mutating configStore, old references to config objects remain immutable. New messages fetch fresh config.

5. **Module logger pattern:** Used createModuleLogger('ProfileConfigWatcher') for consistent logging across the codebase.

6. **Singleton instances per profile:** getProfileLoader() maintains a Map to return same instance for same profile ID, preventing duplicate watchers.

### Gotchas

1. **File system timing (Windows):** File change detection can be flaky depending on file I/O timing. Solved by using awaitWriteFinish and reasonable debounce delays.

2. **Vitest timeout syntax:** Vitest 4 removed the `{ timeout: X }` object syntax for `it()`. Changed to second parameter: `it(name, fn, timeout)`.

3. **Chokidar pattern matching:** By default watches everything in directory. Must filter in the change handler with `filePath.endsWith('.json')` to ignore non-JSON files.

4. **Relative paths:** ConfigStore uses `join(process.cwd(), 'src', 'assistant', 'data')` instead of `__dirname` because esbuild bundles into dist/ changing __dirname context.

5. **Import paths in tests:** Test file in tests/lib requires imports as `../../src/lib/...` not `../src/lib/...` due to directory depth.

### Integration Notes

To integrate hot-reload into the running application:
1. After configStore.init() in src/index.ts, call ProfileLoader.initialize()
2. On graceful shutdown, call ProfileLoader.destroy() to cleanup watcher
3. ConfigStore already emits 'reload' events that other modules listen to
4. No changes needed to message pipeline — it already calls configStore.getXXX() on each request

*   **Zero Division:** Ensure the rate calculation (`completed / started`) handles cases where `started` is zero to prevent errors.
*   **State Rollbacks:** The logic must be robust against users moving backward in the workflow to avoid incorrect counts.
*   **Atomicity:** Rely on Redis's atomic operations (`hincrby`) to prevent race conditions.
