6.  Use a library like `natural` to perform the TF-IDF calculation on the cleaned texts for each intent group.
7.  From the TF-IDF results, extract the top 2-3 terms with the highest scores for each intent. These are the `suggested_keywords`.
8.  Format the final results into the specified JSON structure and print to standard output.

*   **Performance:** Processing 30 days of data could be memory-intensive. The script should process data in streams or chunks if memory becomes an issue.
*   **Zero Results:** The script should handle cases where no escalated conversations are found for the given period and return an empty or informative message.
*   **Keyword Quality:** TF-IDF might suggest single letters, numbers, or nonsensical terms. Apply a post-filter to suggestions (e.g., minimum length of 3 characters).

**Subject: Technical Brief for US-217: Booking Cancellation Workflow Test Suite**

This task involves creating a new integration test suite, not modifying existing Frappe/Python code. The context is a TypeScript/Node.js application.

**1. Files to Modify/Create:**
*   **Create:** `src/tests/workflows/booking-cancellation.integration.test.ts`. This is the primary deliverable.
*   **Reference:** `src/lib/workflow-executor.ts`. This file contains the core state machine logic that the tests will target.
*   **Reference:** `src/assistant/data/workflows.json`. This file defines the `booking_cancellation_workflow` and its transition rules.

**2. Key DocTypes/Hooks (Analogues):**
*   **Workflow Definition:** The `booking_cancellation_workflow` object within `workflows.json` acts as the blueprint for the state machine.
*   **Data Models:** The tests will interact with data models for Bookings, User Profiles, and Credits.
*   **Audit Table:** Assertions must be made against the `workflow_audit` database table to verify state transition logging.

**3. Recommended Implementation Approach:**
*   Utilize the existing test framework (likely Vitest, given `vitest.config.ts`).
*   In the new test file, create scenarios for each acceptance criterion.
*   For each test:
    *   Set up the initial database state (e.g., create a booking record for a specific profile).
    *   Instantiate and run the `WorkflowExecutor` for the cancellation event.
    *   Query the database to assert that the booking status, credit calculations, and audit logs are correct.

**4. Edge Cases & Gotchas:**
*   **Profile-Specific Policies:** The cancellation logic branches based on the profile ("Pelangi", "Makan", "Southern"). Tests must validate the unique outcomes for each profile.
*   **Transactional Rollbacks:** Create a test that intentionally fails mid-workflow to ensure all associated database changes are correctly rolled back, as stipulated in the acceptance criteria.
*   **State Consistency:** Verify that the booking record, credit ledger, and audit logs are all perfectly synchronized after a workflow completes or fails.
